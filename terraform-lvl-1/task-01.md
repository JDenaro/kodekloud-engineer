# Task 01: Create Key Pair Using Terraform

The Nautilus DevOps team is strategizing the migration of a portion of their infrastructure to the AWS cloud. Recognizing the scale of this undertaking, they have opted to approach the migration in incremental steps rather than as a single massive transition. To achieve this, they have segmented large tasks into smaller, more manageable units. This granular approach enables the team to execute the migration in gradual phases, ensuring smoother implementation and minimizing disruption to ongoing operations. By breaking down the migration into smaller tasks, the Nautilus DevOps team can systematically progress through each stage, allowing for better control, risk mitigation, and optimization of resources throughout the process.

For this task, create a key pair using Terraform with the following requirements:

Name of the key pair should be `datacenter-kp`.

Key pair type must be `rsa`.

The private key file should be saved under `/home/bob/datacenter-kp.pem`.
The Terraform working directory is `/home/bob/terraform`. Create the `main.tf` file (do not create a different `.tf` file) to accomplish this task.

Note: Right-click under the **EXPLORER** section in VS Code and select Open in Integrated Terminal to launch the terminal.

## Task Requirements

1. Create an AWS key pair named `datacenter-kp`.
2. Generate the key pair using the RSA algorithm.
3. Save the generated private key to `/home/bob/datacenter-kp.pem`.
4. Use `/home/bob/terraform` as the Terraform working directory.
5. Create the configuration in `main.tf`.

## Solution

The solution uses three Terraform resources. `tls_private_key` generates the RSA key material, `aws_key_pair` registers the public key with AWS, and `local_sensitive_file` writes the private key to the required local path with restrictive file permissions.

The lab already provided `provider.tf`, so the Terraform and provider blocks were not duplicated in `main.tf`. The `main.tf` file was created from the VS Code Explorer as requested.

### 📄 Step 1: Create main.tf in the Terraform working directory

In the VS Code Explorer, open `/home/bob/terraform`, right-click the directory, select **New File**, and name the file `main.tf`.

Add the following configuration:

```hcl
resource "tls_private_key" "datacenter_kp" {
  algorithm = "RSA"
}

resource "aws_key_pair" "datacenter_kp" {
  key_name   = "datacenter-kp"
  public_key = tls_private_key.datacenter_kp.public_key_openssh
}

resource "local_sensitive_file" "datacenter_kp" {
  filename        = "/home/bob/datacenter-kp.pem"
  content         = tls_private_key.datacenter_kp.private_key_pem
  file_permission = "0400"
}
```

> **Why:** `tls_private_key` creates a private key and exposes its public key in OpenSSH format. `algorithm = "RSA"` selects the required RSA algorithm. `aws_key_pair` creates the EC2 key pair in AWS; `key_name` sets its AWS name and `public_key` registers the public key generated by the TLS resource. `local_sensitive_file` creates a local file containing sensitive content. `filename` sets the required destination, `content` receives the generated PEM private key, and `file_permission = "0400"` restricts access to the file owner.

### ⚙️ Step 2: Initialize Terraform

Open the integrated terminal from the `/home/bob/terraform` directory and run:

```bash
terraform init
```

Expected result:

```text
Terraform has been successfully initialized!
```

> **Why:** `terraform init` initializes the working directory, reads the existing Terraform configuration, and installs the required provider plugins. Because `provider.tf` already existed, `main.tf` only needed to define the resources.

### 🧭 Step 3: Review the execution plan

```bash
terraform plan
```

The plan should include these three resources for creation:

```text
tls_private_key.datacenter_kp
aws_key_pair.datacenter_kp
local_sensitive_file.datacenter_kp
```

> **Why:** `terraform plan` previews the changes Terraform intends to make without applying them. The three resources represent the generated RSA key, the AWS key pair containing its public key, and the local private-key file.

### 🚀 Step 4: Apply the configuration

```bash
terraform apply
```

When Terraform asks for confirmation, enter:

```text
yes
```

Expected result:

```text
Apply complete! Resources: 3 added, 0 changed, 0 destroyed.
```

> **Why:** `terraform apply` creates or updates the resources described by the configuration. The dependency references cause Terraform to generate the private key before registering its public key with AWS and writing the private key file locally. The confirmation prevents accidental changes unless the operator explicitly approves the plan.

### ✅ Step 5: Confirm the Terraform result

The successful apply should report three created resources:

```text
Apply complete! Resources: 3 added, 0 changed, 0 destroyed.
```

The expected final state is:

- AWS key pair name: `datacenter-kp`
- Key algorithm: RSA
- Private key path: `/home/bob/datacenter-kp.pem`
- Private key file permission: `0400`

> **Why:** The apply summary confirms that Terraform created the key resource, the AWS key pair, and the local sensitive file. The configured attributes match every requirement from the challenge.

## Best Practices

- **Keep the configuration in the requested file.** Store the resources in `/home/bob/terraform/main.tf` and leave the existing `provider.tf` unchanged.
- **Use resource references for dependencies.** Referencing `tls_private_key.datacenter_kp.public_key_openssh` ensures that the AWS key pair uses the public key generated by Terraform.
- **Protect the private key file.** File permission `0400` allows only the owner to read the generated PEM file.
- **Review before applying.** Run `terraform plan` before `terraform apply` so the intended resources and attributes are visible.
- **Protect Terraform state.** The managed `tls_private_key` resource can store private key material unencrypted in Terraform state. Treat the state file as sensitive and avoid committing it to source control.
- **Use generated keys only where appropriate.** The Terraform TLS provider documentation recommends caution with managed private keys for production environments; this approach is suitable for the disposable training lab.
