# Day 55: Kubernetes Sidecar Containers

We have a web server container running the nginx image. The access and error logs generated by the web server are not critical enough to be placed on a persistent volume. However, Nautilus developers need access to the last 24 hours of logs so that they can trace issues and bugs. Therefore, we need to ship the access and error logs for the web server to a log-aggregation service. Following the separation of concerns principle, we implement the Sidecar pattern by deploying a second container that ships the error and access logs from nginx. Nginx does one thing, and it does it well - serving web pages. The second container also specializes in its task - shipping logs. Since containers are running on the same Pod, we can use a shared emptyDir volume to read and write logs.

## Specific Requirements:

1. Create a pod named `webserver`.
2. Create an `emptyDir` volume named `shared-logs`.
3. Create a regular container in the `webserver` pod from the `nginx:latest` image named `nginx-container`, and an init container from the `ubuntu:latest` image named `sidecar-container`.
4. Add the following command to the `sidecar-container` `"sh","-c","while true; do cat /var/log/nginx/access.log /var/log/nginx/error.log; sleep 30; done"`
5. Mount the `shared-logs` volume in both containers at `/var/log/nginx`. Ensure all containers are in a running state.

`Note:` The `kubectl` utility on the `jump-host` has been configured to work with the Kubernetes cluster.

## Solution

Kubernetes implements native sidecars as a special type of init container. A container declared under `initContainers` with the container-level `restartPolicy: Always` starts before the main application and continues running throughout the Pod's lifetime. This is essential here because the log-reading command contains an infinite loop: without the sidecar restart policy, a traditional init container would never complete and Nginx would never start.

Both containers mount the same `emptyDir` volume at `/var/log/nginx`. Nginx writes its access and error logs there, while the sidecar reads the same files without adding log-shipping responsibilities to the web server container.

### 📝 Step 1: Create the Pod Manifest

```bash
vi webserver.yaml
```

Add the following configuration:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: webserver
spec:
  initContainers:
    - name: sidecar-container
      image: ubuntu:latest
      restartPolicy: Always
      command: ["sh", "-c", "while true; do cat /var/log/nginx/access.log /var/log/nginx/error.log; sleep 30; done"]
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/nginx

  containers:
    - name: nginx-container
      image: nginx:latest
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/nginx

  volumes:
    - name: shared-logs
      emptyDir: {}
```

> **Why:** `metadata.name` assigns the required Pod name. `sidecar-container` is intentionally placed under `initContainers`, while its container-level `restartPolicy: Always` makes it a Kubernetes-native sidecar that remains active alongside the application. The `command` starts a shell with `sh -c`, repeatedly reads both Nginx log files, waits 30 seconds, and repeats. `nginx-container` remains under the regular `containers` section because it is the main application. Both `volumeMounts` refer to `shared-logs` at `/var/log/nginx`, and the Pod-level `volumes` section creates that shared storage as an `emptyDir`.

### 🚀 Step 2: Create the Pod

```bash
kubectl apply -f webserver.yaml
```

Kubernetes confirmed the creation:

```text
pod/webserver created
```

> **Why:** `kubectl apply` sends the declarative manifest to the Kubernetes API. The `-f` option identifies `webserver.yaml` as the file containing the resource definition. Kubernetes starts the restartable init container first and then proceeds to the Nginx application container once the sidecar has started.

### 🔍 Step 3: Check the Pod State

```bash
kubectl get pods
```

Both containers became ready and remained running:

```text
NAME        READY   STATUS    RESTARTS   AGE
webserver   2/2     Running   0          8s
```

> **Why:** `kubectl get pods` presents a concise workload status. `READY 2/2` confirms that the Nginx application and the restartable sidecar are both ready, while `STATUS Running` proves that the infinite sidecar command did not block the main container from starting.

### ✅ Step 4: Verify the Sidecar Lifecycle and Shared Volume

```bash
kubectl describe pod webserver
```

The sidecar appeared under `Init Containers` but remained active:

```text
Init Containers:
  sidecar-container:
    Image:         ubuntu:latest
    State:          Running
    Ready:          True
    Restart Count:  0
    Mounts:
      /var/log/nginx from shared-logs (rw)
```

The main application container was also running and mounted the same volume:

```text
Containers:
  nginx-container:
    Image:          nginx:latest
    State:          Running
    Ready:          True
    Restart Count:  0
    Mounts:
      /var/log/nginx from shared-logs (rw)
```

The volume definition confirmed the required ephemeral storage:

```text
Volumes:
  shared-logs:
    Type:       EmptyDir (a temporary directory that shares a pod's lifetime)
```

> **Why:** `kubectl describe pod webserver` displays the lifecycle state, command, image, and mounts for each container as well as the Pod's volumes. Seeing `sidecar-container` as a running init container confirms the native sidecar behavior provided by `restartPolicy: Always`. Seeing `/var/log/nginx from shared-logs` under both containers proves that the log reader and Nginx share the same filesystem location. The `EmptyDir` type confirms that the logs are temporary and tied to this Pod's lifetime.

## Best Practices

- **Use `restartPolicy: Always` for native sidecars.** A long-running container under `initContainers` needs this container-level policy; otherwise, a traditional init container must finish before the main application can start.
- **Separate supporting responsibilities.** Keeping log handling in a sidecar allows Nginx to focus on serving traffic and lets the logging behavior evolve independently.
- **Treat `emptyDir` logs as ephemeral.** The volume survives individual container restarts but is removed when the Pod is deleted or replaced. Use persistent or external storage when logs must survive the Pod lifecycle.
- **Avoid unbounded local log growth.** Production workloads should configure log rotation, storage limits, or reliable forwarding to prevent an `emptyDir` volume from consuming excessive node storage.
- **Pin image versions in production.** The lab requires `latest`, but immutable tags or image digests make application and sidecar behavior reproducible.
